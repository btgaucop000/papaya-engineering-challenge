# 1. Thiết kế đề xuất

## Kiến trúc tối giản

```text
React UI
   │
   ▼
NestJS API
   │
   ├── WorkflowApplicationService
   │       ├── Pure WorkflowEngine
   │       └── PostgreSQL transaction
   │              ├── claims
   │              ├── claim_audit
   │              ├── payment_requests
   │              └── outbox
   │
   └── Outbox worker ──► mock notifications/payment/console
```

Cấu trúc logic đề xuất:

- `workflow-engine`: TypeScript thuần, không dùng decorator NestJS, ORM hay HTTP.
- NestJS chịu trách nhiệm xác thực, transaction, repository và chuyển đổi lỗi sang HTTP.
- React đọc metadata transition từ API, không hardcode state hay role.
- PostgreSQL lưu state hiện tại, facts, counters, audit, payment request và outbox.
- JSON định nghĩa workflow; PostgreSQL dùng `text`, không dùng PostgreSQL enum để state mới không cần migration.

API tối thiểu:

- `GET /claims/:id`
- `GET /claims/:id/transitions`
- `POST /claims/:id/transitions`
- `GET /claims/:id/audit`
- Các endpoint nhập dữ liệu prerequisite được mô tả ở phần 7.

Engine nhận dữ liệu dạng:

```ts
evaluate(
  definition,
  claimSnapshot,
  actor,
  transitionCommand,
  now
): TransitionPlan | WorkflowError
```

`TransitionPlan` chỉ mô tả state mới, counter updates và effect descriptors. Engine không tự truy cập DB hay gọi dịch vụ ngoài.

# 4. Workflow JSON và preconditions

Không nên cho config chứa JavaScript expression hoặc `eval`. Dùng DSL nhỏ, xác định trước:

```json
{
  "version": "claims-v1",
  "initialState": "SUBMITTED",
  "states": [
    { "id": "SUBMITTED", "label": "Submitted" },
    { "id": "DOCUMENTS_VERIFIED", "label": "Documents verified" }
  ],
  "counters": [
    {
      "key": "informationRequests",
      "incrementOnTransition": "request_more_info",
      "maximum": 3,
      "exceededError": {
        "code": "CYCLE_LIMIT_EXCEEDED",
        "message": "Maximum information requests exceeded — escalate to team lead"
      }
    }
  ],
  "transitions": [
    {
      "id": "approve_claim",
      "from": "UNDER_ASSESSMENT",
      "to": "APPROVED",
      "authorizedRoles": ["assessor"],
      "preconditions": {
        "all": [
          {
            "fact": "assessment.reportComplete",
            "operator": "eq",
            "value": true,
            "error": "Assessment report is incomplete"
          },
          {
            "fact": "claim.amountMinor",
            "operator": "lteFact",
            "valueFact": "policy.limitMinor",
            "error": "Claim amount exceeds policy limit"
          }
        ]
      },
      "effects": [
        {
          "type": "console_notification",
          "target": "member",
          "template": "claim_approved"
        },
        {
          "type": "create_payment_request"
        }
      ]
    },
    {
      "id": "close_rejected_claim",
      "from": "REJECTED",
      "to": "CLOSED",
      "authorizedRoles": ["system"],
      "preconditions": {
        "any": [
          {
            "fact": "appeal.expiresAt",
            "operator": "lteNow"
          },
          {
            "fact": "appeal.memberAcknowledged",
            "operator": "eq",
            "value": true
          }
        ]
      },
      "effects": [{ "type": "archive_claim" }]
    }
  ]
}
```

DSL tối thiểu cần:

- Nhóm: `all`, `any`, `not`
- Toán tử: `eq`, `exists`, `lte`, `gte`, `lteFact`, `lteNow`
- Fact paths trên snapshot đã được server chuẩn hóa
- Clock được inject để test thời gian quyết định được
- Mỗi leaf có mã/thông báo lỗi cụ thể

Cycle limit là counter tổng quát, không phải logic hardcode cho tên state. Trước khi áp dụng transition `request_more_info`, engine kiểm tra `current < maximum`; counter chỉ tăng khi transaction commit thành công.

# 6. State, audit và concurrency

Transaction đề xuất:

1. `BEGIN`.
2. Lock claim bằng `SELECT ... FOR UPDATE`.
3. Kiểm tra `idempotencyKey` và `expectedVersion`.
4. Đánh giá transition, role, preconditions và cycle trên snapshot đã lock.
5. Cập nhật state, counter và increment `version`.
6. Insert một audit record.
7. Insert outbox effects và payment placeholder nếu cần.
8. `COMMIT`.

Nếu bất kỳ bước nào lỗi, toàn bộ transaction rollback.

Các trường chính:

- `claims`: `state`, `context jsonb`, `workflow_counters jsonb`, `workflow_version`, `version`
- `claim_audit`: trường bắt buộc từ brief, cộng `transition_id`, `claim_sequence`, `workflow_version`, `idempotency_key`
- `payment_requests`: `status`, `external_reference`, `idempotency_key`
- `outbox`: effect payload, attempt count, next attempt, last error, status

Audit bất biến:

- Runtime DB role chỉ có `SELECT` và `INSERT` trên `claim_audit`.
- `UPDATE`/`DELETE` bị revoke.
- Có thể thêm trigger chặn update/delete làm lớp bảo vệ thứ hai.
- Sửa sai bằng record bù mới, không thay đổi record cũ.
- Dùng `claim_sequence` để sắp xếp; timestamp có thể trùng.
- Unique constraint trên `(claim_id, claim_sequence)` và `(claim_id, idempotency_key)`.

Concurrency:

- Row lock serialize transition trên cùng claim.
- Client gửi `expectedVersion`.
- Request đến sau với version cũ nhận `409 VERSION_CONFLICT`.
- Retry do mất response dùng cùng `idempotencyKey` và nhận lại kết quả cũ, không tạo audit/effect trùng.

# 7. Side effect, payment và retry

Không thể đảm bảo transaction PostgreSQL và hệ thống ngoài “exactly once”. Mô hình hợp lý là transactional outbox + at-least-once delivery + idempotency.

Luồng approval:

1. Transition sang `APPROVED`, audit, payment row `PENDING` và outbox effect được commit cùng transaction.
2. Worker gọi mock payment-request handler sau commit.
3. Thành công: payment row chuyển thành `CREATED`.
4. Thất bại: claim vẫn `APPROVED`, audit không bị đảo ngược; outbox lưu lỗi và retry.
5. `APPROVED → PAYMENT_INITIATED` chỉ hợp lệ khi payment row là `CREATED`.

Luồng payment initiation:

- Transition sang `PAYMENT_INITIATED` enqueue `trigger_payment_system`.
- Handler thất bại thì retry effect, không chạy lại transition.
- Mỗi lần gọi external/mock dùng idempotency key ổn định, ví dụ `payment:{claimId}:{approvalAuditId}`.
- Confirmation cập nhật payment row sang `CONFIRMED` và lưu reference.
- Sau đó finance mới có thể close claim.

Với challenge, handler chỉ cần log ra console và có fake handler cấu hình để fail/succeed trong test. Dead-letter UI và vận hành retry thủ công có thể để ngoài phạm vi.

# 8. Nhập dữ liệu để thỏa preconditions

Không nên cho client sửa trực tiếp `context jsonb` hoặc counter. Dùng endpoint/domain form có allowlist:

| Fact | Nguồn dữ liệu đề xuất |
|---|---|
| All required documents present | Document metadata; server tự tính tất cả required documents có trạng thái valid |
| Assessor assigned | Team lead chọn assessor |
| Assessment report complete | Assessor lưu report và đánh dấu complete |
| Claim amount / policy limit | Amount nhập lúc tạo claim; policy snapshot do server lưu |
| Rejection reason | Input bắt buộc trong modal transition reject |
| Missing-info description | Input bắt buộc trong transition request-info |
| New information received | Document/info record có thời điểm sau lần request-info gần nhất |
| Payment request created | Chỉ payment worker cập nhật |
| Payment confirmed/reference | Mock payment callback hoặc finance simulation endpoint |
| Appeal expired | Tính từ `appeal.expiresAt` và injected clock |
| Member acknowledged | Endpoint acknowledgement |
| Cycle counter | Chỉ workflow transaction cập nhật |

React có thể dùng ba khu vực:

- Claim facts/prerequisite data
- Available transitions, gồm role và lý do đang disabled
- Audit timeline

## 1. Dữ liệu và thao tác theo từng bước

| Transition | Dữ liệu/precondition | Cập nhật trong transaction | Sau commit |
|---|---|---|---|
| `SUBMITTED → DOCUMENTS_VERIFIED` | `[R]` Tất cả required documents present và valid | State + audit | Mock notify assessor team |
| `DOCUMENTS_VERIFIED → UNDER_ASSESSMENT` | `[R]` Có `assessorId` | State + audit; đặt `assessmentStartedAt = now` | Không cần external call |
| `UNDER_ASSESSMENT → PENDING_INFO` | `[R]` Có missing-info description | State + audit; tăng `informationRequestCount`; lưu description và `lastInfoRequestedAt`; invalidate report cũ | Mock notify member |
| `PENDING_INFO → DOCUMENTS_VERIFIED` | `[R]` Có thông tin mới | State + audit; đặt `assessmentStartedAt = null` | Không cần external call |
| `UNDER_ASSESSMENT → APPROVED` | `[R]` Report complete và amount ≤ policy limit | State + audit; tạo duy nhất mock payment request cho transition này | Mock notify member |
| `UNDER_ASSESSMENT → REJECTED` | `[R]` Report complete và có rejection reason | State + audit; lưu reason và `appealExpiresAt` | Mock notify member |
| `APPROVED → PAYMENT_INITIATED` | `[R]` Payment request tồn tại | State + audit; đổi mock request sang `INITIATED` | Gọi mock payment system |
| `PAYMENT_INITIATED → CLOSED` | `[R]` Payment confirmed | State + audit | Mock notify member với reference |
| `REJECTED → CLOSED` | `[R]` Appeal expired hoặc acknowledged | State + audit; đặt `archivedAt` | Không cần external call |

## 2. Phân loại effects

Config vẫn định nghĩa side effects, nhưng mỗi handler đăng ký một phase:

```json
{
  "type": "create_payment_request",
  "phase": "transactional"
}
```

hoặc:

```json
{
  "type": "notify_member",
  "phase": "afterCommit"
}
```

### Transactional handlers

- `start_assessment_timer`
- `reset_assessment_timer`
- `create_payment_request`
- `mark_payment_initiated`
- `archive_claim`

Chúng chạy trong cùng transaction với state/counter/audit. Lỗi sẽ rollback toàn bộ.

`create_payment_request` chỉ xuất hiện trong config của `approve_claim`; engine không tự tạo payment request dựa trên destination state hay cho transition khác.

### After-commit handlers

- `notify_assessor_team`
- `notify_member`
- `trigger_payment_system`

Chúng chạy đồng bộ ngay sau commit, được bọc `try/catch`.

Nếu mock effect lỗi:

- State và audit vẫn thành công.
- API vẫn trả HTTP thành công cho transition.
- Response có thể chứa `effectWarnings`, ví dụ:

```json
{
  "transition": "SUCCESS",
  "state": "PAYMENT_INITIATED",
  "effectWarnings": [
    {
      "effect": "trigger_payment_system",
      "message": "Mock payment call failed; transition was committed"
    }
  ]
}
```

- UI hiển thị “Transition completed; mock effect failed”, không hiển thị nút retry transition.
- `[O]` Không có durable retry; nếu process chết sau commit nhưng trước effect thì effect có thể bị mất.

## 3. Quy tắc dữ liệu được đề xuất

### Request-info

`[A]` Mỗi transition thành công `UNDER_ASSESSMENT → PENDING_INFO` được tính là một request:

- Lần 1–3 được phép.
- Lần 4 bị từ chối trước khi ghi state/audit/counter.
- Request chưa được member trả lời vẫn tiêu thụ một lượt.

### Thông tin mới

`[A]` Thao tác “Record new information” lưu `lastInfoReceivedAt`.

Precondition quay lại `DOCUMENTS_VERIFIED` là:

```text
lastInfoReceivedAt > lastInfoRequestedAt
```

Cách này ngăn tài liệu của vòng trước được tái sử dụng cho vòng sau.

### Report cũ

`[A]` Khi vào `PENDING_INFO`:

- Đặt `assessmentReportComplete = false`.
- Giữ nội dung/report metadata cũ để tham khảo.
- Sau khi quay lại assessment, assessor phải xác nhận report mới trước khi approve/reject.

### Assessment timer

`[A]`:

- `DOCUMENTS_VERIFIED → UNDER_ASSESSMENT`: đặt timer bằng thời điểm hiện tại.
- `PENDING_INFO → DOCUMENTS_VERIFIED`: reset về `null`.
- Lần tiếp theo vào `UNDER_ASSESSMENT` sẽ bắt đầu timestamp mới.

### Appeal expiry

`[A]` Khi reject, đặt `appealExpiresAt = now + 14 days`.

- Rejection scenario bắt buộc có thể dùng member acknowledgement để close ngay.
- Test expiry dùng injected clock, không đợi thời gian thật.
- Không xây dựng appeal workflow.

### System role

`[A]` `system` không xuất hiện trong demo-user selector.

UI có nút “Run eligible system action”; server tự tạo actor cố định:

```json
{
  "userId": "demo-system",
  "role": "system"
}
```

Không có scheduler trong phạm vi này.

## 4. Config và missing facts

`[A]` Đề xuất fail closed ở hai tầng:

1. Khi khởi động, config được kiểm tra bằng schema và fact catalog:

   - State/transition không tồn tại: config invalid.
   - Operator/handler không đăng ký: config invalid.
   - Fact path không thuộc catalog: config invalid.
   - App không khởi động với workflow lỗi.

2. Khi chạy:

   - Fact hợp lệ nhưng chưa có giá trị làm precondition thất bại với `FACT_MISSING`.
   - Missing/null không được tự chuyển thành `false`, `0` hay điều kiện đạt.
   - Ngoại lệ duy nhất là operator tường minh như `exists`.

Config-only extension chỉ được dùng:

- Fact path đã đăng ký
- Role string hiện có
- Operator hiện có
- Transactional/after-commit handler hiện có
- State lưu dưới dạng `text` và business data trong `jsonb`

Do đó thêm state/transition demo không cần sửa TypeScript hoặc schema DB.
